# ADR-0013: 认证与权限(店主/店员/顾客)

## Status
Accepted

## Date
2026-09-18

## Context
系统涉及三类身份:
- **店主**:首店的核心决策人,要能开通后台、配置活动、审核提现、看数据
- **店员**:店主授权协助日常运营(扫码核销、登记订单),**无提现审核权**
- **顾客**:扫码被邀请的新客 / 老客,要能查看自己的邀请码 / 余额 / 提现

三类身份的认证方式直接影响开通门槛、日常运营负担与安全强度,需要分别决策。

候选方案:

### 店主首次激活(已选 a)
- (a) **微信扫码 + 激活码**(微信号预存白名单) ← 已选
- (b) 邀请码 + 身份证后四位
- (c) 手机号 + 短信验证码 + unionID 三重绑定
- (d) 完全免验证,只看微信身份

### 店员加入(已选 a)
- (a) **店主生码,店员扫码绑定** ← 已选
- (b) 店员提交申请,店主审核通过
- (d) 钉钉/企业微信 SSO

### 顾客认证强度(已选 b,后被 ADR-0016 替代)
- (a) 仅微信 OpenID
- (b) **OpenID + 手机号** ← 原选,因 AppID 为个人主体无法调用 `getPhoneNumber`,已被 ADR-0016 替代
- (c) OpenID + 手机号 + 实名认证
- (d) 仅 unionID

## Decision

### 店主:微信扫码 + 一次性激活码

店主首次进入管理端小程序时:
1. 必须用预设的**店主微信号**(实施时由我们人工预存到 `customers` 集合的 `role: "owner"` 文档)
2. 扫码后云函数比对 `openid` 与白名单
3. 白名单匹配 → 弹一次性激活码输入框(8 位,离线生成或打印交付)
4. 激活码通过 → 角色写入 `role: "owner"`,进入后台

> **首店实施**:每个店只配 1 个店主,激活码离线打印交付,丢失需联系我们后台重置。

### 店员:店主生码,店员扫码绑定

1. 店主在「店员管理」页面点击「邀请新店员」
2. 后端生成 6 位一次性邀请码(10 分钟有效),写入 `staff_invitations` 集合
3. 店主把邀请码微信发给店员
4. 店员下载管理端小程序 → 输入邀请码 + 微信授权 → 完成绑定
5. 店员角色写 `role: "clerk"`,无提现审核权限

### 顾客:店员代录入 + 手机号+4位短码登录(ADR-0016,替代原 OpenID+手机号方案)

> **已被 ADR-0016 替代**:原方案依赖 `<button open-type="getPhoneNumber">`,但本项目 AppID 为**个人主体**,微信不向个人主体小程序开放 `getPhoneNumber` 接口;且不接入短信验证码(资质成本)。故改为店员线下代录顾客手机号的方案。

现行顾客认证流程(详见 [ADR-0016](./0016-staff-creates-customer.md)):

1. **店员/店主代录入**:店员在管理端录入顾客手机号 → 云函数生成 4 位数字 `customerCode` → 店员口头告知顾客
2. **顾客凭凭证登录**:顾客在顾客端输入「手机号 + 4 位 customerCode」→ 云函数比对 `phoneHash` + `customerCode` 校验
3. **无 token 模型**:顾客端不持 openid、不发 token,每次调用云函数都回传 `{ phone, customerCode }` 由云函数实时校验
4. **手机号只存哈希**:`phoneHash = SHA256(phone + globalSalt)`,不存明文
5. **防爆破**:连续 5 次登录失败锁定该 phoneHash 1 小时(进程内 Map,个人店够用)

> **用户路径**:到店消费 → 店员录入手机号生成编号 → 顾客用「手机号+编号」登录查询余额。无需微信授权,不依赖 `getPhoneNumber`。

### 权限矩阵

| 操作 | 顾客 | 店员 | 店主 |
|---|---|---|---|
| 查看返利余额 | ✓ | ✗(查他人需店主权限) | ✓ |
| 申请提现 | ✓ | ✗ | ✗ |
| 录入订单/核销 | ✗ | ✓ | ✓ |
| 代录入顾客 | ✗ | ✓ | ✓ |
| 节假日配置 | ✗ | ✗ | ✓ |
| 提现审核 | ✗ | ✗ | ✓ |
| 邀请店员(生码) | ✗ | ✗ | ✓ |
| 顾客列表/余额 | ✗ | ✓ | ✓ |
| 审计日志 | ✗ | ✗ | ✓ |

### 关键安全设计

1. **微信号预存白名单**:实施时由我们一次写入,店主自己无法自助新增店主(防越权)
2. **激活码离线**:8 位数字 + 字母,一次性使用,失败 3 次锁定 24 小时
3. **店员邀请码短期**:10 分钟过期,绑定 Q50 次/天/IP(防爆破)
4. **手机号只存哈希**:云函数不写明文到数据库;退款时需要手机号做二次验证,走缓存 + 重新授权
5. **openid 不暴露**:仅在云函数内使用,前端只持有云函数返回的 `customerId`(UUID)

## Consequences
- (+) **开通门槛适中**:店主用微信扫码 + 8 位激活码,不需要短信服务
- (+) **店员流程丝滑**:店主发邀请码,店员扫码即用,无需账号密码
- (+) **顾客身份可关联手机号**:防薅羊毛能力强(同一手机号不能注册多个邀请人)
- (+) **店主无法自助新增店主**:避免越权风险
- (-) **首店激活码需人工交付**:每个新店上线都需要我们介入(可接受,因开店是低频)
- (-) **店员邀请码 10 分钟过期**:店主偶尔需要重发,体验稍重
- (-) **手机号哈希化后无法看明文**:退款等场景需要让顾客重新授权,稍麻烦
- (-) **微信号换绑 = 店主账号丢失**:店主微信号是核心凭证,需在激活码使用文档中明确警示

### ADR-0016 变更补充(顾客端)
- 顾客端已由「微信授权 + getPhoneNumber 自助注册」改为「店员代录 + 手机号+4位短码登录」
- 顾客不持 openid、无 token,每次云函数调用回传凭证由云函数实时校验
- 顾客邀请码自助生成流程已移除;邀请关系由店员录入顾客时指定 `inviterId`
- 详见 [ADR-0016](./0016-staff-creates-customer.md)

## Known Risks
- **店主微信号被盗 = 后台被盗**:激活码 8 位是最后防线,需要在 audit_log 里监控「店主异常时间登录」
- **店员与店主同微信号**:微信下不允许同一 openid 同时拥有 owner 和 clerk 角色,云函数互斥校验
- **顾客手机号换绑**:手机号只存哈希,换绑需要走「原手机号短信验证」或「店主后台强制解绑」(首期仅店主后台可解)
